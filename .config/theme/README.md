# Desktop theme system

One palette file drives every themed component. Nothing else should contain a
raw colour value.

    ~/.config/theme/palette.toml              <- the only file you edit
    ~/.config/theme/theme-apply               <- renders + live-reloads
    ~/.config/theme/palette-<name>.toml       <- saved alternative palettes

## Usage

    theme-apply              # render all configs and reload live
    theme-apply --dry-run    # show what would change, write nothing
    theme-apply --check      # verify colour contracts only (exit 1 on gap)
    theme-apply --no-reload  # write files but don't touch running apps

## Changing the theme

**Change the accent only** -- edit `[roles] accent` in `palette.toml` to any
key in `[palette]` (`blue`, `teal`, `peach`, ...), then run `theme-apply`.

**Swap to a saved palette** -- palettes are kept side by side:

    cp ~/.config/theme/palette-catppuccin-mocha.toml \
       ~/.config/theme/palette.toml && theme-apply

**Add a new theme** -- replace the `[palette]` block with another set of named
colours, then repoint the three mapping blocks (`[roles]`, `[terminal]`,
`[extra]`) at the new keys. Renderers never read palette keys directly, only
those mappings, so any palette works once they are filled in. `theme-apply`
exits with an error naming any mapping that points at a colour that
does not exist.

## How it works

Each component is themed through its *own* native include mechanism, so your
real configs stay hand-editable and are never overwritten. `theme-apply` only
writes the small generated file each one pulls in:

| Component | Mechanism | Generated file |
|---|---|---|
| Hyprland | `require("theme")` | `hypr/theme.lua` |
| hyprlock | `source =` | `hypr/theme-colors.conf` |
| Waybar   | `@import url()` | `waybar/colors.css` |
| swaync   | `@import url()` | `swaync/colors.css` |
| fuzzel   | `include=` | `fuzzel/colors.ini` |
| kitty    | `include` | `kitty/current-theme.conf` |
| WezTerm  | `color_scheme =` | `wezterm/colors/palette.toml` |
| GTK 3/4  | `@import 'colors.css'` | `gtk-{3,4}.0/colors.css` |
| Qt / KDE | `[Colors:*]` blocks | `kdeglobals` + `color-schemes/*.colors` |
| Wallpaper | path file read by `start-wallpaper.sh` | `hypr/theme-wallpaper` |

Generated files carry a `GENERATED by theme-apply` banner. Edit the palette,
not them -- they are overwritten on every run.

## Two things worth knowing

**GTK is Breeze-shaped, Catppuccin-coloured.** The Breeze GTK theme references
~86 `@*_breeze` colour variables but never defines them; upstream they come
from `colorreload-gtk-module` reading the KDE colour scheme. We generate them
from the palette instead. That is why GTK apps follow this palette without any
Catppuccin GTK theme package being installed. `theme-apply --check` verifies
every name the installed theme dereferences is still satisfied -- run it after
a `breeze-gtk` package update.

**Qt reads kdeglobals, not the .colors file.** `ColorScheme=` is only a label.
Applying a scheme means merging its `[Colors:*]` blocks into `kdeglobals`,
which `theme-apply` does. Non-colour sections are preserved. Qt apps pick up
changes on next launch, not live.

## Reload behaviour

| Component | Reload |
|---|---|
| Hyprland, Waybar, swaync | live |
| GTK | live for most apps |
| kitty | new windows (live if remote control is enabled) |
| WezTerm | auto-reloads on config change; new windows always |
| Qt / Dolphin / file dialog | next app launch |

## Palette file structure

    [palette]   raw named colours of the theme -- never read directly
    [roles]     semantic UI names   -> palette keys  (accent, bg, fg, ...)
    [terminal]  the 16 ANSI slots   -> palette keys  (red, bright_blue, ...)
    [extra]     odds and ends       -> palette keys  (cursor, link_visited)
    [opacity]   per-surface alpha, not colour

Two top-level keys sit outside those blocks: `name` (used for the KDE scheme
name) and the optional `wallpaper`, a filename inside `hypr/wallpapers/`. When
set, `theme-apply` resolves it into `hypr/theme-wallpaper`, which both
`start-wallpaper.sh` and hyprlock's `$wallpaper` read -- so desktop and lock
screen follow the theme. A palette with no `wallpaper` leaves the current one
alone.

Keeping the mappings separate from the colours is what makes a theme swap a
data change rather than a code change. All sixteen `[terminal]` slots are
required; `theme-apply` refuses to run if any are missing.

## Current theme

**Akane** (茜, madder red) -- ported from
[Grenish/omarchy-akane-theme](https://github.com/Grenish/omarchy-akane-theme)
at commit `bfe2285`. Colours are taken verbatim from upstream `colors.toml`,
and the ANSI block from upstream `alacritty.toml`, so the port is faithful
rather than approximated. Vermillion torii (`#e15a48`) on dusk navy
(`#12101c`), with warm sunset foreground (`#f0c4a8`) instead of grey. The
`ee`/`aa` opacities reproduce upstream's exact border rgba values.

Upstream also specifies `Yaru-red` icons. We stay on `breeze-dark` instead:
Breeze icons are stylesheet-driven and inherit the KDE accent, so folders
already render in Akane vermillion. `yaru-icon-theme` is packaged in Fedora if
you want the literal upstream icon set.
